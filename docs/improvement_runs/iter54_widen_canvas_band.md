# Итерация №54 — узкая канва заставляла колонки переноситься при пустом поле

## Генерация: пропущена по сети (тридцать девятый раз подряд), за секунды

## Что увидел глазами

Прогнал новый `scripts/offline_probe.py` на длинном контенте и посмотрел
рендеры. На слайде-сравнении Т—Ж Учебного правая колонка переносилась —
«Автоматический сбор по / расписанию», — при том что справа пустовало два дюйма
карточки.

## Разбор

```
колонки:            0.39–3.89 и 4.09–7.59  (по 3.50in)
контентные границы: 0.39–7.59  — взяты из СОБСТВЕННОГО текста канвы
шаблонная полоса:   0.39–8.98
карточка:           до 9.6in
```

То есть канва отдаёт полосу уже, чем layout шаблона, и колонка не дотягивает до
одной строки буквально чуть-чуть. iter32 уже разбирала этот же довод для СЛИШКОМ
НИЗКОЙ полосы канвы; здесь ровно то же по ширине.

## Почему нельзя расширять вслепую

Замер: у Универсального шесть канв узкие ПО ЗАМЫСЛУ — справа стоит фото. У
Учебного таких две (канвы 4 и 5). Расширить их — значит положить текст на арт,
то есть заменить один дефект другим, хуже.

Поэтому каждая сторона двигается только в пространство, где НИКАКОЙ картинки
нет; полноэкранный фон препятствием не считается — на нём и так всё лежит.

## Проверка

```
Учебный, канвы 0,1,2,6,7,8,9,10,11 → расширяются до 8.98
Учебный, канвы 4,5                → остаются 4.67 (справа фото)
колонки сравнения: 3.50 → 4.20in, перенос ушёл
```

**Посмотрел рендеры глазами**: у Учебного и у Универсального колонки заняли всю
ширину и читаются одной строкой; ничего не наехало.

Отдельно проверил риск, который сам внёс: прошёлся по всем пробным декам и
посчитал существенные (>20%) наложения текста на арт. Единственное — титул
обложки Универсального, 0.39; ровно такое же наложение есть на НЕТРОНУТОМ
шаблоне, то есть это авторская компоновка, а не регресс.

Тесты: **166 passed** (+1). Тест держит обе стороны правила на одном шаблоне:
свободная канва расширяется, канва с фото — нет. На HEAD падает с
`clear canvas kept a narrow band: 7.59in against the template's 8.98in`.

## Сравнение с прошлой итерацией

iter53 сделала пробник, и он окупился дважды: сначала нашёл отравленные кэши, а
теперь этот дефект — на слайде, который на КОРОТКОМ контенте выглядел нормально
(короткие пункты в 3.50in не переносятся). Это второй случай подряд, когда
дефект виден только на реалистичном тексте.

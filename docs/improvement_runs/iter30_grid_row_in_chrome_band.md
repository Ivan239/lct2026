# Итерация №30 — половина сетки шаблона не использовалась никогда

## Генерация: пропущена по сети (пятнадцатый раз подряд)

Прогон поднял **GigaChat-2-Max × survey-31** и завис на OAuth
(`ngw.devices.sberbank.ru:9443`): 7+ минут при 1 секунде CPU — это сетевые
ретраи, не разбор шаблона. Деки нет → **оценку 10.1 и взвешенный итог не
выставлял, оценивать нечего.**

Всё ниже — офлайн: `generate()` чистый Python, проверка рендером и глазами.

## Что чинил — пункт 2 очереди, найденный замером в iter29

У Т—Ж Универсального слайд-список — это **6 пунктов сеткой 3×2**. Мы всегда
использовали только 3. Разбор:

```
слайд 5.62in высотой, chrome-полоса = 0.79in → нижняя граница на 4.83in
ряд 1: top=4.18  низ=4.41   chrome=False   ← видим
ряд 2: top=4.91  низ=5.15   chrome=True    ← НЕ видим
настоящая мебель того же шаблона: «ТЕМА ПРЕЗЕНТАЦИИ» top=0.31, номер стр. top=5.28
```

Chrome-тест — «низкий бокс, прижатый к краевой полосе». Нижний ряд сетки
заходит в полосу на 0.32in и попадает под него целиком. `get_capacity` отдавала
3, и половина макета шаблона, ради которого шаблон и берут, не использовалась
ни разу.

Геометрический тюнинг `is_chrome_shape` не годится: ряд действительно стоит
низко (top=4.91 против границы 4.83), и симметричный вариант теста его тоже
считает мебелью. Значит различать надо не по полосе, а по **сетке**: бокс в
ПОЛНОЙ сетке рядом с не-chrome ячейками — это контент, в какой бы полосе он ни
стоял. Номера страниц и шапки не образуют сеток с контентными боксами.

## Реализация

- `_find_slot_boxes` берёт кандидатов из всех текстовых шейпов, а не из
  chrome-фильтрованных.
- Страховка: сетка целиком из chrome отбраковывается (повторяющаяся подвальная
  полоса не станет мишенью для заполнения).
- Замер перед правкой по ВСЕМ пяти реальным шаблонам: меняется **ровно один
  слайд** (Универсальный №2, 3 → 6), сеток целиком из chrome не возникает нигде.

### Побочный эффект, который поймал только рендер

Заполнив нижний ряд, получил бейджи `01,01,01,01,02,03`. Причина: бейджи ряда 2
лежат в chrome-полосе, а `_renumber_static_slide_numbers` переписывает любой
цифровой chrome-бокс в номер страницы — `_is_page_number` пропускает всё до 99,
так что «04»/«05»/«06» честно сошли за номера и стали тремя «01».

Claimed-пометка тут не помогает: она защищает только от `_clear_unclaimed_text`.
Бейджи, которыми управляем мы, теперь несут имя `SlotBadge` (по образцу
`IMAGE_PLACEHOLDER_NAME`), и перенумератор страниц их пропускает.

## Проверка

```
Универсальный, 6 пунктов   бейджи 01 02 03 04 05 06
Универсальный, 3 пункта    бейджи 01 02 03            (без регресса)
Моно,          6 пунктов   бейджи 01 02 03 04 05 06
ёмкости bullet_list по всем шаблонам: изменилась одна (Универсальный №2)
```

**Посмотрел рендер глазами**: сетка 3×2 заполнена целиком, нумерация идёт в
порядке чтения, интервалы ровные, белым по чёрному читается, ничего не наезжает
и не уходит за край слайда.

Проверил отдельно, что нижний ряд не выпадает из финального QA: `enforce_text_fits`
идёт по `slide.shapes` без chrome-фильтра, слепой зоны нет.

Тесты: **140 passed** (+2). Оба новых падают на HEAD — `ёмкость 3 вместо 6` и
`нумерация ['01','02','03']`.

## Сравнение с прошлой итерацией

iter29 вернула нумерацию пунктов, и ровно её замеры показали, почему у
Универсального ёмкость 3: нижний ряд читался как мебель. Эта итерация закрывает
находку. Три итерации подряд идут в одну точку — выход должен воспроизводить
макет дизайнера: сначала кегль (iter28), потом нумерация (iter29), теперь
полный размер сетки.

## Очередь

1. **[генерация] Статический номер страницы и брендовый «2025» стираются**
   `_clear_unclaimed_text`. Прямой путь (миловать «chrome + цифры») закрыт
   экспериментом iter29; решение — явный claim там, где мы ими управляем.
   Механизм `SlotBadge` из этой итерации даёт готовый образец, как это
   пометить.
2. **[harness] Card-макеты: считать пиксели ВНУТРИ геометрии текстовых боксов.**
3. **[генерация] Служебный текст шаблона** («ТЕМА ПРЕЗЕНТАЦИИ» — заглушка).
4. **[генерация] Пустая правая половина** на канве с фотографией.

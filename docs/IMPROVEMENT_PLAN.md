# План улучшений СлайдоГена — заметки для реализации

Этот документ — самоинструкция для будущих сессий разработки. Написан так, чтобы можно
было открыть его без контекста прошлых обсуждений и начать делать. Пункты отсортированы
по приоритету: сверху — максимум пользы за минимум усилий.

Контекст проекта на момент написания (июль 2026):
- Пайплайн: `template_parser` (OOXML → структура) → `design_system` (классификация
  архетипов слайдов) → `content_parser` (бриф → блоки контента через GigaChat) →
  `matcher` (блок ↔ слайд/SYNTHESIZE) → `generator` (заполнение/синтез) → рендер.
- Известные слабые места (все всплывали на реальном шаблоне "Short Survey 2024",
  файл `output/templates/custom_30e96c06e2d47ec3.pptx`, 31 слайд):
  - оценка размера текста по количеству символов (`generator/text_fit.py`) неточна —
    дрейф иконок-буллетов на длинных списках, неидеальная подгонка шрифта;
  - структурная сигнатура (`design_system/signature.py`) слишком строгая — визуально
    однородная семья слайдов (стат-слайды 5-19) режется на 10+ групп;
  - контент генерируется ДО матчинга с фикс. "ровно 3 пункта", потом чинится
    `resize_block`-ом постфактум — лишние вызовы и хрупкость;
  - регрессии промптов ловятся вручную на проде (пустые заголовки после добавления
    section_divider — реальный случай);
  - QA-прохода нет вообще, наложения/пустоту находил пользователь глазами.

## Пункт 1. Точные метрики шрифта: fontTools + embedded fonts — ✅ СДЕЛАНО (июль 2026)

Реализация: `src/fonts/metrics.py` (FontMetrics поверх fontTools: точные ширины
глифов из hmtx/cmap, line_height из hhea, coverage/supports_cyrillic;
FontResolver — резолвинг имён включая theme-токены "+mn-lt"/"+mj-lt", кэш).
`text_fit.py` переписан: greedy-перенос по словам с реальными ширинами
(точность < 1% против независимого замера PIL), учёт дефолтных инсетов бокса
(0.2"), char-count оставлен fallback-ом при metrics=None. Резолвер прокинут
через generate() → fillers/synthesizers (опциональный параметр, старые вызовы
работают без него).

ВАЖНЫЙ ФАКТ: embedded-шрифты нашего тестового шаблона сжаты MicroType Express
(EOT flag 0x04) — декомпрессора в open source нет, поэтому для них работает
донорская ветка (Arial-класс). Ветка парсинга embedded готова и сработает на
несжатых fntdata (PowerPoint desktop обычно встраивает несжатые).

Попутно закрыты два реальных бага дрейфа иконок-буллетов:
(а) высота строки считалась по шрифту, а оригинальные абзацы деки имеют
line_spacing=1.5 — теперь читаются реальные line_spacing/space_before/space_after
каждого абзаца (_paragraph_line_height_pt);
(б) _align_left_edges сдвигал текст на колонку иконок И ломал их детекцию
(фильтр "иконка левее текста") — теперь иконки ищутся до выравнивания, и при
их наличии выравнивание пропускается.
Проверено рендером: 7 иконок = 7 строк, ровная колонка, без наложений.

--- (исходное описание ниже) ---

**Зачем.** Весь `generator/text_fit.py` сейчас — оценка "средняя ширина символа ≈
0.62 × размер шрифта". Из-за этого: неточная подгонка размера, дрейф иконок-буллетов
(`_reposition_bullet_icons` в generator.py), перестраховочные запасы высоты. Это
крупнейший источник визуальных дефектов.

**Ключевой факт.** PPTX умеет встраивать шрифты: `ppt/fonts/*.fntdata` внутри zip.
Предупреждения LibreOffice "EOT out of spec: no blank loca table found!" при рендере
нашего тестового шаблона — прямое доказательство, что в нём embedded fonts ЕСТЬ.
Формат — EOT-обёртка вокруг TTF (иногда чистый TTF).

**Как делать:**
1. Новый модуль `src/fonts/metrics.py`. Зависимость: `fontTools` (в requirements.txt).
2. Извлечение: открыть pptx как zip, найти `ppt/fonts/*.fntdata`; распарсить
   `ppt/presentation.xml` → `<p:embeddedFontLst>` — там соответствие "имя шрифта →
   r:id → файл". EOT: попробовать срезать EOT-заголовок до TTF (обычно TTF начинается
   с `\x00\x01\x00\x00` или `OTTO`; искать смещение сигнатуры). Если не парсится —
   не падать, идти в fallback.
3. API модуля:
   - `get_font_metrics(pptx_path, font_name) -> FontMetrics | None`
   - `FontMetrics.text_width_pt(text, size_pt) -> float` — через `hmtx`-таблицу
     (ширины глифов) + `cmap` (символ → глиф) + units_per_em из `head`.
   - `FontMetrics.supports_cyrillic() -> bool` — покрытие U+0410–U+044F в cmap
     (заодно закрывает проблему "Aeroport без кириллицы" — см. Пункт 7 ниже).
4. Fallback-цепочка, если embedded нет: скачать/включить в репо 2-3 открытых шрифта
   (Inter, PT Sans) как "метрические доноры"; выбор донора — по эвристике
   (serif/sans по названию). Последний fallback — текущий char-count.
5. Переписать `text_fit.py`: `estimate_wrapped_lines` → честный greedy line-breaking
   по словам с реальными ширинами (`fit_font_size` остаётся, но внутри — точные числа).
   Сигнатуры функций сохранить, чтобы не трогать вызовы в generator/synthesizer.
6. Проверка (без токенов): для 3-4 слайдов сравнить рассчитанную ширину строки с
   фактической на рендере (пиксели PNG / DPI). Расхождение < 5% — успех.

**Ловушки:** кэшируйте FontMetrics по (pptx_hash, font_name) — парсить TTF на каждый
текстбокс расточительно. Run без font.name (наследование от темы) — брать шрифт
темы из `extract_theme`.

## Пункт 2а. Модель шага строки = правило рендера (июль 2026, автономная итерация)

Дожат «дрейф иконок-буллетов», который считался закрытым Пунктом 1. Диагноз по
рендерам реальной деки (8505a62c): LibreOffice/PowerPoint считают процентный
межстрочный интервал (a:spcPct) НЕ от метрик шрифта, а от классического
«одна строка = 1.2 em»: шаг = 1.2 × размер × процент. Калибровка по трём
независимым замерам PNG (18pt/150% → ровно 32.4pt; 21pt и 24pt сходятся после
учёта автоужатия LO fontScale=0.9). Цепочка дефекта: фиттер не учитывал ни
line_spacing, ни вертикальные инсеты бокса → текст «влезал» по нашей оценке,
но переполнял бокс по правилу рендера → LO молча ужимал через normAutofit →
иконки, расставленные под исходный размер, прогрессивно съезжали.

Сделано: `text_fit.paragraph_pitch_pt` (единая модель: spcPct → 1.2-правило,
spcPts → как есть, нет — метрики шрифта) прокинута в фиттинг, QA-проход и
позиционирование иконок; фиттинг и QA вычитают реальные tIns/bIns;
`harmonize_clone_font_sizes` возвращает список ужатий, и
`generator._realign_icons_after_resize` перекладывает иконки под финальный
размер (раньше пост-QA ужатие оставляло их под старый). Попутно: латентный баг
`isinstance(Length, int)` — абсолютные spcPts/spcBef читались как множители.

Проверено без LLM: сквозной generate() на custom_30e96c06e2d47ec3 (слайды 24,
26, 28 — 8/7/4 пунктов) + рендер + пиксельные замеры: шаг строк совпал с
моделью (36.0/41.4/32.4pt), дельты иконок к строкам константны (нет
накопления), клон-сценарий с harmonize — иконки на шаге финального размера.
Тесты: test_text_fit_pitch.py, test_clone_harmony.py::test_icons_follow_harmonized_size.

## Пункт 2б. Единый стиль ранов в заполненных списках (июль 2026, автономная итерация)

Второй по заметности артефакт тех же рендеров: в списке с иконками часть
пунктов целиком фиолетовые. Причина: шаблон красит акцентные ФРАЗЫ внутри
пунктов схемными цветами; мы пишем новый текст в первый ран абзаца — у одних
абзацев он акцентный, у других обычный. Сделано:
`generator._dominant_reference_run` (стиль, покрывающий больше всего символов
шейпа) + `unify_format` в `_set_paragraph_text`: все написанные строки
приводятся к доминирующему стилю; однородные шаблоны не меняются. Два
подводных камня: (1) схемные цвета — `color.rgb` КИДАЕТ исключение, сравнивать
и копировать надо `theme_color`/`brightness` (`_run_color_key`); (2) «не
скопировать цвет» ≠ «унифицировать» — если у источника цвет унаследованный, с
целевого рана надо СНЯТЬ явную заливку (`_clear_run_fill`), иначе акцент
остаётся. Проверено рендером слайда-24-шаблона (7 пунктов одним цветом,
иконки на местах) и tests/test_style_unify.py.

## Пункт 2д. Честные горизонтальные поля в бюджете ширины (19.07.2026, автономная итерация)

Боевая дека f78f14b1 (слайд 2, шаблонный слайд 28 custom_30e96c06e2d47ec3):
пункт «Неконсистентность оформления между авторами» перенёсся на вторую
строку и разложил колонку иконок (4-й пункт остался без маркера). Разбор:
все расчёты ширины (`_usable_width_in`) вычитали плоские 0.2", а у реального
бокса lIns=0, rIns=0.1" и абзацный marL=0.25" под колонку иконок — бюджет
завышен на 0.15" (11pt), фактический запас «гарантии одной строки» усох с 5%
до ~1.5%. Сделано: `text_fit.frame_horizontal_margins_in` (реальные инсеты,
дефолт 0.1"×2) + `paragraph_indent_in` (marL + max(indent,0); отрицательный
indent — висячий буллет, бюджет не расширяет) + `horizontal_margins_in`
(инсеты + максимальный отступ непустых абзацев); опциональный `margins_in`
прокинут через estimate_wrapped_lines / estimate_block_height_in /
fit_font_size / fit_font_size_single_line и все вызовы в генераторе
(включая пер-абзацные поля в `_reposition_bullet_icons`) и qa/geometry.
Проверено: generate() на слайдах 28 (4 иконки) и 24 (7 иконок) с теми же
текстами → рендер → пиксельный скан: все пункты одной строкой, дельты
иконка-строка константны (~15px, без накопления). Тесты:
tests/test_horizontal_margins.py (3 шт). Попутный факт: сама дека f78f14b1
была сгенерирована НЕперезапущенным бэкендом со старым кодом (18pt там, где
даже прошлая версия дала бы 17pt) — правило «перезапускать uvicorn после
правок» написано кровью ещё раз.

## Пункт 2е. Слотовое заполнение списков + снос фантомных абзацев (19.07.2026, автономная итерация)

Найдено QA-свипом по 69-слайдовому шаблону (слайд 2, однобоксовый стат-фолбэк
с 3 иконками): текст ужат рендером до ~17pt при наших 24pt, иконки мимо строк,
третья — в пустоту, левая кромка рваная. Разбор: бокс хранит контент в слотах
(абзацы 0/3/5/7) со спейсерами между ними и хвостом, включая абзац из
'\x0b\x0b\x0b' (по strip() «пустой», рендерится тремя переносами). Секвенальное
заполнение писало в спейсеры (смешанные marL → рваная кромка), а «очистка»
хвоста оставляла 7 фантомных строк → бокс переполнен → LO normAutofit ужимал
всё → иконки, посчитанные от 24pt, разъезжались. Хелперы _content_slot_indices
/ _extend_content_slots уже лежали в generator.py мёртвым кодом с прошлой
сессии — теперь подключены. Сделано в _set_paragraph_texts: заполнение по
слотам; физическое удаление всего после последнего пункта; нормализация числа
спейсеров между пунктами до МИНИМАЛЬНОГО зазора шаблона (неровные 2-1-зазоры —
артефакт прозы, не дизайн); _unify_paragraph_indents (мажоритарные
marL/indent). _set_run_text тоже удаляет абзацы[1:] вместо очистки.
_reposition_bullet_icons переписан: шагает по ВСЕМ абзацам в порядке документа
(спейсер продвигает на свою строку — размер из его собственных ранов), иконки
ставятся у контентных. get_capacity(bullet_list) зеркально считает слоты, не
все абзацы. Проверено: рендеры слайдов 1/2/66 шаблона 78dc + слайдов 24/28
шаблона 30e9 (регрессии нет), пиксельные замеры ровных шагов; ноль LLM.
Тесты: tests/test_slot_fill.py (3 шт), суммарно 43.
Смежно: qa/geometry.enforce_text_fits раньше выкидывал пустые абзацы из
оценки высоты — т.е. был слеп ровно к фантомным строкам, которые и ловит;
теперь внутренние спейсеры считаются строкой каждый (хвостовые пустые
обрезаются — у нетронутых шаблонных слайдов это нижний отступ по дизайну).
Инвариант «здоровая дека → 0 правок QA» перепроверен на обоих свипах.

## Пункт 2ж. Вертикальное центрирование синтезированных слайдов (20.07.2026, автономная итерация)

Тот же класс дефекта, что 2в, но для слайдов, которые строим с нуля: в деке
f78f14b1 синтезированный two_column_comparison (слайд 6) занимал верхнюю треть,
низ пустой — шаблон 30e9 не имеет ни two_column, ни divider, ни closing, так
что синтез — частый путь даже на основном демо-шаблоне. Сделано в
`synthesizer.py`: `_centered_top` — заголовок остаётся на месте (консистентно
с нативными слайдами), а контентный блок (колонки / KPI-ряд / буллеты)
центрируется между низом заголовка и нижней границей inferred bounds по
оценке высоты через `estimate_block_height_in` с метриками резолвера
(колонки — max из двух, буллеты — плюс межпунктовые space_before, KPI — фикс.
1.8"). Контент выше границ области не двигается (переполнение → offset 0).
Проверено рендером на custom_30e96c06e2d47ec3 (4 синт-слайда: колонки и KPI
в середине, 12-пунктовый плотный список не сдвинут) + tests/test_synth_center.py.

## Пункт 2з. Свип пресетов: выбор титула по верхней полосе + фон пресета A (20.07.2026, автономная итерация)

Первый пиксельный свип ПРЕСЕТНЫХ шаблонов (генерация без LLM + рендер) нашёл два
дефекта, оба видимые пользователю с первого клика:

1. **Титул уезжал в KPI-бокс.** `_pick_title_shape` без плейсхолдеров брал шейп
   с максимальным шрифтом — на стат-слайде пресета A числа (48pt) крупнее
   титула (30pt), титул записывался в первый номерной бокс и ВСЕ пары
   число/лейбл сдвигались на бокс. Фикс: кандидаты ниже верхней четверти
   контентного диапазона (min top → max bottom по шейпам) получают штраф 0.5 к
   размеру шрифта — титул в своей полосе побеждает крупные числа, а херо-титул
   кавера посреди слайда всё ещё бьёт мелкие подписи. Тесты: tests/test_title_pick.py.
2. **Пресет A — светлый текст на белом.** `make_synthetic_templates.py` ставил
   навы-фон только титульному слайду, а цвет текста (220,220,225) подобран под
   навы — контентные слайды рендерились почти невидимыми. Фон теперь на каждом
   слайде, пресеты перегенерированы (геометрия не менялась — кэши/архетипы
   валидны). Известный смежный зазор: синтезированные слайды берут цвета из
   ТЕМЫ (дефолтная у синтетических пресетов), а не из фактических цветов
   слайдов — на тёмном пресете синт-слайд будет белым. Отложено: реальные
   корп. шаблоны несут тему честно, а пресеты после фикса синтеза не требуют.

## Пункт 2и. Синтез по наблюдаемому стилю деки, не по теме (20.07.2026, автономная итерация)

Закрыт зазор из 2з: тема OOXML часто ВРЁТ про реальный вид деки — ручные деки
и наши пресеты красят раны напрямую, а theme1.xml остаётся офисным дефолтом;
синтезированный дивайдер на пресете A выходил белым Calibri-слайдом в
навы-Georgia деке. Сделано: `generator/deck_style.py` —
`observe_deck_style(prs)` (мажоритарное голосование по реальным слайдам:
явный solid-фон слайда из сырого XML — НЕ через slide.background.fill, который
get-or-add'ом мутирует деку при чтении; цвета ранов RGB с весом по символам,
жирные/крупные ≥24pt → accent+major_font, остальные → text+minor_font; имена
шрифтов «+mj-lt»/«+mn-lt» — теневые токены темы, отбрасываются) и
`apply_observed_style(theme, observed)` (оверлей на палитру/шрифты только
уверенных фактов + вето по контрасту: |ΔLum| < 80 между итоговыми text/bg →
текст заменяется на белый/чёрный). Подключено в generate() только для
SYNTHESIZERS; филлеры продолжают жить на стилях заполняемых слайдов.
Проверено рендерами: пресет A — синт-дивайдер/колонки/closing в навы+оранж
Georgia; 30e9 — синт-слайды в тёмном фирменном стиле деки и шрифте Aeroport
(раньше — фиолетовый Calibri-дефолт). Тесты: tests/test_deck_style.py (3 шт).

## Пункт 2в. Вертикальное центрирование недозаполненных боди (июль 2026, автономная итерация)

Третий наблюдённый дефект деки 8505a62c: stats_kpi через однобоксовый фолбэк —
две строки прижаты к верху бокса высотой 5" («слайд пуст на 80%»). Шаблон
custom_30e96c06e2d47ec3 настоящих стат-слайдов не имеет (семья 5–19 — чарты,
исключены по oversized-картинкам), так что фолбэк легитимен — проблема только
в композиции. Сделано: `generator._center_if_underfilled` — если текст
занимает < 45% полезной высоты бокса (по той же модели шага строк) и у шейпа

- **Клонирование нативных слайдов** (`generator._clone_slide` + matcher):

  шаблонного слайда со всеми иконками/фонами/типографикой (rels картинок
  переносятся, r:embed переписываются). SYNTHESIZE остался только для ролей,
  которых в шаблоне нет вообще.
- **Подстановка шрифтов в превью** (`rendering/render.py`): отсутствующие на
  рендер-хосте семейства (реальные имена из name-таблиц через fontTools)
  подменяются на Arial в копии для LibreOffice — уходит фирменный артефакт
  "наползающие буквы" на всех превью; скачиваемый .pptx не меняется.
- **Сироты-иконки**: при контенте короче числа иконок лишние удаляются,
  оставшиеся выравниваются по своим строкам (раньше — требование точного

- **Spec без дискового кэша** (`api/main.py`): слоты пересобираются на каждый
  запрос (~0.07с на 69 слайдов) — закэшированный `_spec.json` молча протухал
  при каждом изменении `get_capacity` и уже дважды маскировал реальные фиксы.

**Зачем (исходная мотивация).** Наложения текста, оверфлоу и полупустые слайды пользователь находил
глазами. Всё это ловится геометрией из финального pptx — ноль токенов.

**Как делать:**
1. Новый модуль `src/qa/geometry_checks.py`:
   - `check_slide(slide, slide_w, slide_h, metrics_provider) -> list[Issue]`
   - Проверки:
     a) **Пересечения**: для каждой пары непустых текстбоксов — пересечение
        прямоугольников (left/top/width/height уже в EMU). Порог: пересечение
        > 5% площади меньшего → issue "overlap".
     b) **Оверфлоу**: estimated_height(текст, ширина бокса, размер шрифта из Пункта 1)
        > высота бокса × 1.1 → issue "overflow".
     c) **Пустота**: сумма площадей непустых текстбоксов и картинок < 15% площади
        слайда → issue "sparse" (тот самый "пустой на 80% слайд").
   - `Issue`: `{slide_idx, kind, severity, details}`.
2. Вызов в конце `generate()` (generator.py) по каждому слайду финального файла.
3. Реакция по видам:
   - overflow → авто-фикс: уменьшить шрифт на шаг и перепроверить (цикл максимум 3 итерации);
   - overlap → попытаться сдвинуть нижний бокс вниз, если под ним есть место; иначе warning;
   - sparse → warning в ответ API (поле `warnings` в /api/generate), фронт показывает
     бейдж "слайд N может выглядеть пусто" на превью.
4. Эти же проверки — основа метрик качества (Пункт 5) и regression-тестов.

**Ловушки:** slide-number/date/footer плейсхолдеры исключать (см.
`_BORING_PLACEHOLDER_TYPES` в generator.py — уже есть). Иконки-буллеты (мелкие
картинки) не считать в "пустоту" наравне с контентом — брать площадь, но понимать,
что 6 иконок × 0.04% ничего не добавляют.

## Пункт 3. Кластеризация слайдов вместо LLM-классификации — ✅ СДЕЛАНО (июль 2026, без CLIP)

Реализовано в `src/design_system/clustering.py` + `fingerprint_cache.py`; старый
`signature.py` (точное равенство кортежа) удалён. Решение отличается от плана ниже —
CLIP оказался не нужен, хватило двух бесплатных сигналов:

1. **Структурная дистанция** — Dice-пересечение мультисетов фигур на двух
   гранулярностях: (роль, размер, текст-бакет) и то же + ячейка сетки 4×3.
   Частичное совпадение вместо точного равенства: слайд с 3 буллетами и с 5 —
   одна семья. Агломеративная кластеризация (average linkage), порог 0.4.
   На реальных данных зазор огромный: одна семья = 0–0.13, разные = 0.83–1.0.
2. **Визуальный штраф** — 8×8 grayscale-миниатюра рендера (яркость, MAD) +
   знаки горизонтальных градиентов (dHash). max() двух компонент; превышение
   над 0.35 добавляется к дистанции с весом 2.0. Ловит фон уровня мастера,
   который парсер не видит. Штраф мягкий, не жёсткое вето: одна шумная пара
   (крупный текст в разных местах) не блокирует слияние, поддержанное
   остальными парами.
3. **LLM — один вызов на медоид кластера**, не на слайд.
4. **Межшаблонный кэш фингерпринтов** (`output/parsed/fingerprint_cache.json`):
   ключ — sha256 от placed-мультисета (только геометрия, без текста клиента —
   безопасно шарить между клиентами). Голосование: подтверждение +1, конфликт
   −1, на нуле — замена. Кэшируются только уверенные не-"other" результаты.
   Экономика: типовые корп. раскладки классифицируются один раз на всю базу
   клиентов; у пресетов A и B фингерпринты уже совпали (0 вызовов на второй).

Результат на 69-слайдовом survey-деке: 69 слайдов → 19 кластеров (~1 сек, чистый
Python + PIL), визуальная проверка монтажей — семьи собраны как видит человек
(9 chart-слайдов вместе, 8 фото-дивайдеров вместе, 4 фиолетовых дивайдера вместе).
CLIP/torch как зависимость не понадобились; вариант ниже оставлен как справка.

<details><summary>Исходный план (CLIP, не реализован)</summary>

**Зачем.** Структурная сигнатура режет визуально единую семью слайдов на много групп
(31 слайд → 16 групп, а человек видит ~8). Каждая лишняя группа — лишний LLM-вызов и
шанс ошибки. Embedding-кластеризация бесплатна (локальная) и видит то, что видит человек.

**Как делать:**
1. Зависимости: `open_clip_torch` или `sentence-transformers` (модель типа
   `clip-ViT-B-32`). CPU достаточно: 31 слайд ≈ секунды.
2. Новый модуль `src/design_system/visual_clusters.py`:
   - вход: список PNG-рендеров (уже есть из `rendering/render.py`);
   - `embed_slides(png_paths) -> np.ndarray`;
   - `cluster(embeddings, threshold≈0.87) -> {cluster_id: [slide_indices]}` —
     агломеративная кластеризация по косинусной близости (scipy/сам поиск связных
     компонент по порогу — проще и предсказуемее k-means, k заранее неизвестен).
3. Новый порядок в `api/main.py::_process_template`:
   a) структурная сигнатура (`signature.py`) — точный дедуп (остаётся, бесплатно);
   b) CLIP-кластеризация поверх групп из (a) — склейка похожих;
   c) LLM-классификация — по ОДНОМУ представителю каждого финального кластера
      (как сейчас, `classify_slide_from_structure`), результат — на весь кластер.
4. Порог 0.87 подобрать на тестовом шаблоне: стат-слайды 5-19 должны склеиться,
   title-слайды с section_divider — НЕ должны. Записать выбранный порог сюда.
5. Исключение chart-слайдов (has_oversized_picture, `common/pictures.py`) оставить —
   оно ортогонально кластеризации.

**Ожидаемый эффект:** 16 групп → 6-8 кластеров; LLM-вызовов на шаблон вдвое меньше;
классификация стабильнее (один результат на всю семью, не разнобой по слайдам).

**Ловушки:** рендеры должны быть одного размера; нормализовать embeddings перед
косинусом; на шаблонах < 5 слайдов кластеризация вырождается — просто пропускать шаг (b).

## Пункт 4. Slot-спека шаблона + двухфазная генерация контента — ✅ СДЕЛАНО (июль 2026)

Реализация: `src/template_spec/builder.py` (спека, кэш в `parsed/<id>_spec.json`,
ленивое построение для старых шаблонов — бесплатно), `src/content_parser/two_phase.py`
(фаза A outline + фаза B по-блочно с жёсткой валидацией count/title и ретраями),
`matcher.plan_from_outline` (выбор слайда ДО генерации текста; предпочитает
наименьшую ёмкость ≥ запрошенной — растяжение вместо усечения), интеграция в
`api/main.py::_plan_two_phase` с fallback на legacy-путь (`_plan_legacy`) при сбое
любой фазы. Семьи v1 = группировка по роли; место под CLIP-кластеризацию (Пункт 3)
оставлено — она уточнит семьи, не меняя потребителей спеки.
Проверено сквозным прогоном: 7-слотовый слайд заполняется 7 пунктами сразу,
без resize; заголовки не теряются (одно требование на вызов в фазе B).

**Зачем.** Сейчас контент генерируется в вакууме ("ровно 3 пункта"), потом
`resize_block` чинит несоответствие ёмкости (лишний вызов на каждый mismatch),
`_ensure_title` дочиняет пустые заголовки. Это мост, а не архитектура. Системное
решение: сначала узнать, что умеет шаблон, потом генерировать сразу в размер.

**Целевое представление шаблона** (выход обработки, JSON рядом с archetype_map):
```json
{
  "families": [
    {
      "id": "f1",
      "role": "bullet_list",            // из фикс. словаря ролей
      "slide_indices": [24, 26, 28],
      "capacity": {"min": 1, "max": 8}, // из get_capacity по слайдам семьи
      "has_icons": true,
      "has_image_slot": false
    }
  ]
}
```
Роли — закрытый словарь (title, section_divider, bullet_list, stats_kpi,
two_column_comparison, quote, closing, image_caption, other). Семьи — открытые
(сколько нашла кластеризация из Пункта 3).

**Двухфазная генерация:**
1. **Фаза A (outline)**: один вызов GigaChat — бриф + компактное "меню" семей
   (одна строка на семью: роль + диапазон ёмкости). Выход: список
   `{role, family_id | "SYNTH", тема блока в 5-7 словах, target_count}`.
   Меню после кластеризации — 6-8 строк, промпт не разрастается.
2. **Фаза B (текст)**: по одному вызову на блок — "напиши контент блока: роль X,
   тема Y, РОВНО N пунктов, заголовок обязателен". Один маленький запрос = одно
   требование = высокая надёжность (проверено этой сессией: маленькие запросы
   типа resize_block соблюдают count, большой parse_brief — нет).
   Вызовы фазы B можно параллелить.
3. `resize_block` и `_ensure_title` остаются как страховка, но должны срабатывать
   редко (логировать частоту их срабатывания — это метрика деградации фазы B).
4. Бонус на будущее (фронт): outline фазы A показать пользователю на редактирование
   до фазы B — та самая Gamma-подобная UX-фича.

**Порядок работ:** сначала собрать slot-спеку (расширить `_process_template`),
потом переключить `content_parser` на 2 фазы, потом упростить matcher (он станет
тривиальным — family_id уже выбран в фазе A).

   синтез рисует на пустом слайде: фирменные папки-фоны теряются (это пикчи
   слайдов, а не фон темы — observe_deck_style их не видит).
3. **Однообразие фонов у клонов** — семья содержит варианты (жёлтая/зелёная/
   синяя папки), но matcher всегда клонирует одного «лучшего» члена семьи.
4. Обложка/«Спасибо» слиплись с числовым слайдом в один кластер (одинаковые
   папки перевесили визуально) → оба получили stats_kpi.

**План (по приоритету):**
- **8а. Слот-боксы** (масс-дефект): детектор колонок из ≥3 одноразмерных
  текстбоксов с равным шагом; заполнение по одному пункту на бокс; маркеры
  (мелкие AUTO_SHAPE/PICTURE в полосе строки) удаляются вместе с лишними
  боксами; `get_capacity` = число слотов. ✅ СДЕЛАНО (см. ниже).
- **8г. Ротация вариантов семьи**: при повторной роли клонировать РАЗНЫХ
  членов семьи по кругу, а не одного лучшего — вернёт чередование цветов. ✅ СДЕЛАНО.
- **8б. Синтез на клон-канве**: роль без нативного слайда синтезируется не на
  пустом слайде, а на клоне слайда-канвы (член title-семьи с максимальной
  свободной областью): очистить контент, разместить свои боксы в контентной

- **8в. Стайл-карта шаблона** (запрос пользователя «промпты под конкретный
  шаблон, дёшево»): ОДИН LLM-вызов на шаблон при загрузке — по структурным

## Пункт 9. Template Style Profile — единый профиль шаблона — ✅ СДЕЛАНО (20.07.2026)

**Постановка.** Классов шаблонов НЕ бывает — их бесконечность, таксономию не
построить. Единственный масштабируемый путь: не «узнавать тип», а на загрузке
**заставлять каждый шаблон рассказать свою дизайн-логику** и дальше слепо ей
следовать. Тот же принцип уже в проекте (кластеризация по измеренному сходству,
`deck_style` голосованием, кэш фингерпринтов — везде «выучи у ЭТОГО артефакта»,
нигде «распознай известный»). Профиль — это ровно оформление этого принципа в
один артефакт, который питает matcher, промпты, синтез и QA.

**Эмпирика (проверено попиксельно на 4 несвязанных шаблонах, generic-замер
доминанты по краям слайда):** Т-Ж → 4 плоских фона + фото, нативный порядок
`ABDC·ABD·(фото)·CBAC` (чистый 4-цикл, соседние не совпадают); Survey-31 → 1
фон + акцент-дивайдер (`AAAA…`), ротации нет; пресет B → 1 фон (`AAAA`). ОДНА
generic-функция выдаёт и ритм Т-Ж, и no-op на одноцветном — без единой ветки
`if template == …`. Ротация фонов в коде — не спецкейс Т-Ж, а то, что общее
правило «крути обнаруженную палитру, не повторяя соседние» выдаёт на входе Т-Ж.

**Два тира, оба per-template, оба без таксономии:**
- дёшево/детерминированно — измеримые сигналы (цвет фона, фото/плоский, роль,
  геометрия слотов): покрывают цвето-фото-ритм;
- 1 LLM-вызов, амортизируется — стайл-карта: добирает смысловое, что пиксели
  не видят (тон, длины текстов, метафора, ритм разделов).

### 9.0. Артефакт профиля — `design_system/style_profile.py`

`build_profile(template_path, archetype_map, render_pngs) -> dict`:
```
{
  "palette": [{"hex", "role_affinity": {...}, "slide_indices": [...]}],  # 9.1
  "rotation": {"order": [hex, ...], "confidence": 0..1, "bookends": {"title": hex, "closing": hex}},
  "breathers": [slide_idx, ...],        # full-bleed фото-«паузы»
  "variants": {slide_idx: {"bg": hex, "has_photo": bool, "free_area": 0..1}},  # 9.2
  "style_card": {...} | null,           # 9.4, единственная LLM-часть

```
**Кэширование — раздельное и это принципиально** (урок из Пункта 2: дисковый
кэш дважды маскировал фиксы): измеримая часть (palette/rotation/breathers/
variants) НЕ кэшируется на диск — пересборка бесплатна, считается на каждый
запрос. LLM-часть (`style_card`) кэшируется в `parsed/{id}_style.json` с
версионированием (как `fingerprint_cache.CLASSIFIER_VERSION`) — bump при любом
изменении промпта стайл-карты.

### 9.1. Палитра фонов + инференс ротации (measured, 0 LLM) — заменяет слепую 8г

**Как делать.**
- `slide_background(png)` — доминанта по тонкой рамке краёв (края почти всегда
  фон, не контент); квантизация до 5 бит/канал. Полноэкранное фото → низкая
  доля доминанты / высокий colors-count → вернуть None (это «breather»).
  Проверено: этот замер уже воспроизводит палитру Т-Ж и корректно даёт `AAAA`
  на одноцветном пресете.
- Фон брать ИЗ РЕНДЕРА, не из XML-fill: у Т-Ж «папки» — это PICTURE (декор,
  см. `is_stale_data_picture`), а не solidFill/тема, так что XML-путь их не
  увидит; пиксель рендера работает одинаково для заливки, темы и картинки.
- `discover_palette(bg_by_slide)` — кластеризовать квантованные фоны в палитру
  шаблона (размер 1..N), отбросив None.
- `infer_rotation(native_sequence)` — доля соседних пар с разным цветом =
  confidence; при высокой confidence извлечь канонический цикл; палитра
  размера 1 → ротации нет.
- `bookends` — цвет титульного слайда и цвет closing-слайда (у Т-Ж оба жёлтые:
  дека обрамляется брендовым цветом).

**Ловушки.** Квантовать не слишком грубо (иначе жёлтый и беж сольются) и не
слишком тонко (иначе анти-алиасинг папок даст ложные цвета) — 5 бит выверены.
Confidence-порог обязателен: на `AAAA…` не выдумывать ротацию.

**Проверка.** Без LLM: `infer_rotation` на Т-Ж обязана вернуть 4-цикл с
confidence≈1 и bookend=жёлтый; на Survey/пресете B — confidence низкий, order
пустой. Тест `test_style_profile.py`.

### 9.2. Вариант-осознанные семьи: ротация matcher по ЦВЕТУ, не по индексу

**Зачем.** Сейчас семья = роль, и `plan_from_outline` ротирует членов round-
robin по индексу (8г, слепо). Правильно — выбирать члена так, чтобы фон шёл по
циклу из 9.1 и соседние слайды деки не совпадали по цвету.

**Как делать.** В `template_spec/builder.build_spec` дописать каждому члену
семьи его `variant` из профиля (bg, has_photo, free_area). В
`matcher.plan_from_outline` вести «цветовой курсор»: для каждого следующего
блока целевой цвет = следующий в `rotation.order`; среди кандидатов семьи,
проходящих по ёмкости, предпочесть члена целевого цвета; титул/closing
притянуть к `bookends`. Если ротации нет (confidence низкий) — поведение
вырождается в текущее (ёмкость + round-robin), НИЧЕГО не ломая на одноцветных.

**Ловушка.** Цвет — вторичный критерий ПОСЛЕ ёмкости: нельзя ради цвета
всунуть 5 пунктов в слайд на 3. Порядок: ёмкость-fit → цвет → round-robin.

**Проверка.** Без LLM: план из 8 bullet-блоков на Т-Ж → цвета фонов идут по
циклу, соседние различны, титул и финал жёлтые. Рендер-свип, инспекция.

### 9.3. Синтез на клон-канве в цвете ротации — заменяет 8б

**Зачем.** Роль без нативного слайда (у Т-Ж — two_column/closing) синтезируется
на ПУСТОМ белом слайде → теряются папка-фон, шапка «ТЕМА ПРЕЗЕНТАЦИИ», футер,
номер. Это те самые белые слайды 6–7 из жалобы.

**Как делать.** Вместо белого листа — клонировать «слайд-канву»: члена любой
семьи с максимальным `free_area` в целевом цвете ротации (из профиля), очистить
его контентные боксы (`_clear_unclaimed_text` + снос слотов), разместить
синтезируемые боксы в inferred content-области. Фон/шапка/футер сохраняются
даром. Переиспользует уже готовый `_clone_slide` (после фикса notesSlide/sldId).

**Ловушка.** Канву резать из НЕТРОНУТОГО шаблона до заполнения (как клоны в
`generate`). content-область брать из `layout_bounds.infer_content_bounds`, а не
хардкодом — у разных шаблонов она разная.

**Проверка.** Синтез closing на Т-Ж → жёлтая папка + «Спасибо», не белый лист.
Рендер. Схемная валидация пакета (9.6).

### 9.4. Стайл-карта: 1 LLM-вызов на шаблон + инжект в промпты — заменяет 8в

**Зачем.** Пиксели ловят цвето-ритм, но НЕ смысловые правила: тон, длины
текстов под конкретные боксы, метафору, чего избегать. Это прямой запрос
пользователя — «промпты под конкретный шаблон, качественно, дёшево».

**Как делать.**
- При загрузке, после кластеризации: ОДИН вызов. Вход — компактные структурные
  описания медоидов (`extractor._describe_slide`, layout уже убран) + сводка
  измеримого профиля (палитра, ролевой состав, длины текстов-плейсхолдеров).
  Выход — строгий JSON (валидатор + ретраи, как в two_phase):
  `{tone, length_norms: {role: "N слов"}, metaphor, section_rhythm, avoid: [...]}`.
- Кэш `parsed/{id}_style.json`, версионированный. Стоимость — 1 вызов на
  шаблон НАВСЕГДА, размазывается на все будущие генерации.
- Инжект: преамбула «дизайн-бриф этого шаблона» в `two_phase.OUTLINE_PROMPT` и
  `BLOCK_PROMPTS`. `length_norms` дополнительно — жёстко в валидацию длины
  (кодом, не только в текст промпта — модель формулировкам не следует).

**Ловушка.** Стайл-карта — подсказка, НЕ источник жёстких ограничений: числовые
лимиты (ровно N пунктов) остаются кодовыми. Не кэшировать при ошибке/низкой
уверенности (иначе отравление, как было с фингерпринтами).

**Проверка.** Мок-клиент: валидатор режет кривой JSON, ретраит; инжект реально
попадает в промпт. Один реальный вызов на Т-Ж для глаз-проверки содержания.

### 9.6. Safety-net: схемный guard пакета + метрики прогона

**Схемная валидация (то, чего не хватало 3 итерации по «требуется
восстановление»).** В систему найден официальный OOXML-валидатор ISO-IEC29500
(в skills/pptx/scripts/office). Он мгновенно показал: старые файлы падают на
notesSlide-sharing, новые — `All validations PASSED`. Задача:
- вендорить валидатор+схемы В РЕПО (не зависеть от пути skill-плагина);
- в конце `generate()` — прогон валидации; при провале не отдавать битый файл,
  а падать с понятной ошибкой (или авторемонт, где возможно);
- regression-тест: все фикстурные генерации проходят схему.
Это тот самый дешёвый guard, что ловит порчу ДО пользователя, а не после.

**Метрики прогона** (Пункт 7, поднять сюда): JSON рядом с generated —
adherence ротации, % sparse, % overflow, доля native/clone/synth, schema pass,
частота resize/ensure_title. Регрессионный сигнал между версиями (не пиксели).

## Пункт 10. Типографская гигиена: косяки, которые видит любой человек (21.07.2026)

Диагноз по реальной генерации f916cb3a на шаблоне custom_838830368dac3116
(минималистичный: титулы 51pt + тело 10pt + сетки нумерованных слотов):

1. **Перенос титулов ПО БУКВАМ** («Автоматизаци/я», «Неконсистентнос/ть»):
   фиттинг ужимает по высоте бокса, но не проверяет, что самое длинное СЛОВО
   влезает в ширину — рендер рвёт слово посреди буквы.
2. **Титулы из двух предложений**: промпт просит «до 7 слов», модель кладёт
   двухпредложенные абзацы; кодового лимита не было (выученное правило: модель
   формулировкам не следует — только код).
3. **Сетки слотов R×C** (2 колонки × 3 ряда пар «номер+название»): вертикальный
   слот-детектор видит только левую колонку → правая чистится в «невидимые»
   следы с номерами.
4. **Микротекст**: тело 10pt — дизайн шаблона, но наш фиттер мог ужимать ещё
   ниже; пола не было.

**Реализация:**
- **10а. Word-fit титулов** ✅: `fit_font_size(..., fit_longest_word_width=True)`
  — размер, при котором самое длинное слово помещается в ширину бокса; в
  `_set_run_text`. Слово шире бокса даже на полу → это сигнал контенту (10б),
  не повод к микрошрифту.
- **10б. Кодовые лимиты длины** ✅: `_enforce_title_budget` (≤9 слов: ретрай в
  валидаторе two_phase, финально — усечение до первого предложения/9 слов) и
  bullet ≤72 симв. (обрезка по словам). Плюс легаси-путь.
- **10в. Грид-слоты** ✅: `_find_slot_boxes` обобщён до сеток (группировка по
  (w,h)-форме, допуск равных шагов по X и Y); порядок заполнения row-major;
  парные номер-боксы слева ведут себя как маркеры (лишние удаляются вместе со
  слотом).
- **10г. Пол размера шрифта** ✅: финальный размер ≥ max(9pt, 0.7×reference);
  fit- и QA-пути. Если и на полу не влезает — текст был обязан быть короче
  (10б держит).

Проверка: `test_typography.py` (10 юнитов) + рендер-свипы на
custom_838830368dac3116: сетка 2×3 заполняется row-major с парными номерами

словам (51→44pt: word-fit + bold-фактор 1.05 + 5% рендер-запас — все три
слагаемых калиброваны по реальным рендерам), «Неконсистентность» на полу
размера получает мягкие переносы U+00AD (видимый дефис вместо рубки букв;
алгоритм слогов упрощённый — по гласным, уточнение при желании).

## Пункт 7. Мелочи, которые стоит сделать по пути

- **Кириллица в шрифте**: `FontMetrics.supports_cyrillic()` из Пункта 1 →
  если false, подставлять донора (Inter/PT Sans/Golos) в заполняемые runs И
  показывать warning в ответе API ("шрифт бренда не содержит кириллицу, заменён на X").
  Прозрачность важнее магии.
- **Составной компонент "иконка+строка × N"**: после Пункта 1 у
  `_reposition_bullet_icons` появятся точные высоты строк — дрейф уйдёт. Следующий
  шаг: при синтезе клонировать иконку из шаблона (copy `<p:pic>` element) и
  генерировать компонент целиком, а не текст отдельно от иконок.
- **Кэш классификации по сигнатуре слайда** (не только по хэшу файла): ключ =
  hash(нормализованная сигнатура без текста) + версия классификатора. Стандартные
  layouts повторяются между пользователями. Инвалидация — bump версии при изменении
  логики.
- **Majority-vote для классификации**: 3 дешёвых вызова с голосованием на
  неоднозначных кластерах (confidence=low) — копейки, заметный прирост стабильности.
- **Метрики каждого прогона** (в JSON-лог рядом с generated): % слайдов без
  коллизий, % без оверфлоу, доля native/synthesized/skipped блоков,
  format-compliance rate LLM-вызовов, частота срабатывания resize/ensure_title.
  Это и есть regression-сигнал (сравнивать между версиями, не пиксели).

## Пункт 11 (в план, НЕ реализовано): несовпадение ёмкости слайда и контента

Поставлено пользователем 2026-07-27. Сейчас цикл прогоняется на РЕАЛЬНЫХ шаблонах
(Т—Ж и боевые деки), где это вылезает постоянно — на игрушечных пресетах не было
видно, потому что там одна семья слайдов с щедрыми боксами.

**Проблема.** В оригинальном слайде 3 колонки, а по тексту получается 4 (или
наоборот). То же самое с буллетами, KPI-плашками, пунктами сравнения и любыми
повторяющимися элементами дизайна. Сейчас матчер выбирает слайд ПО ЁМКОСТИ и
жёстко просит у модели ровно `count` элементов (`_validate_block` + ретраи), то
есть контент подгоняется под шаблон. Это безопасно, но:

- содержание режется под вёрстку, а не наоборот — 4-я мысль просто теряется;
- если у шаблона нет семьи нужной ёмкости, роль уходит в синтез, и мы теряем
  дизайн шаблона там, где достаточно было размножить колонку.

**Что решить (варианты, не выбраны):**

1. **Размножение элемента.** Клонировать 3-ю колонку/плашку в 4-ю, пересчитав
   ширины и позиции по сетке слайда. Работает, когда элементы — независимые
   боксы; ломается на художественных композициях (иконки, фоновые фигуры,
   привязанные к конкретным координатам).
2. **Схлопывание.** Оставить ёмкость шаблона и слить 4 мысли в 3 (или вынести
   4-ю на следующий слайд). Требует решения «что объединять» — это работа для
   модели, но с жёсткой проверкой, что смысл не потерян.
3. **Выбор ближайшей ёмкости с осознанной потерей.** Уже частично есть, но
   решение принимается молча — нужно хотя бы фиксировать в warnings, что
   контент ужали, чтобы это было видно в UI и в оценке.
4. **Порог допустимого растяжения.** Например: ±1 элемент — размножаем/убираем
   геометрией; больше — переносим на второй слайд той же семьи.

**Обязательные проверки при реализации:** правило `get_capacity` обязано и дальше
зеркалить порядок выбора фигур филлером (docs/LESSONS.md); любое клонирование
проверять рендером на Т—Ж шаблонах, где колонки несут иконки и фоновые фигуры,
а не только текстбоксы; ловушки клонирования (`<p:bg>`, notesSlide, sldIdLst) —
см. выученные правила.

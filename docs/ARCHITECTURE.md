# Архитектура пайплайна

Решение разделено на слои, между которыми ходят данные, а не вызовы моделей:
парсинг → дизайн-система → спека шаблона → планирование контента → подбор слайда
→ вёрстка → QA → аудит → экспорт. Модель вызывается ровно в двух местах
(классификация слайдов шаблона и генерация текста), всё остальное —
детерминированный код. Это сделано сознательно: качество вёрстки не должно
зависеть от формулировки промпта.

```
 .pptx шаблона                          бриф / контент-пакет
      │                                          │
      ▼                                          │
┌──────────────┐                                 │
│template_parser│ OOXML → структура слайдов      │
└──────┬───────┘                                 │
       ▼                                         │
┌───────────────┐  кластеризация + 1 вызов LLM   │
│ design_system │  на медоид кластера → архетипы │
│               │  стиль-профиль: палитра фонов, │
│               │  ротация цветов, типографика   │
└──────┬────────┘                                │
       ▼                                         ▼
┌───────────────┐                        ┌────────────────┐
│ template_spec │ какие слайды можно     │ content_parser │ план колоды,
│               │ заполнять, сколько     │                │ затем текст
│               │ пунктов и какой длины  │                │ каждого блока
└──────┬────────┘                        └───────┬────────┘
       └───────────────┐      ┌──────────────────┘
                       ▼      ▼
                   ┌────────────┐
                   │  matcher   │ слайд выбирается ДО генерации текста:
                   └─────┬──────┘ ёмкость → цвет ротации → round-robin
                         ▼
                   ┌────────────┐
                   │ generator  │ вёрстка по слотам, кегли по метрикам шрифта,
                   └─────┬──────┘ синтез недостающих ролей на канве шаблона
                         ▼
                   ┌────────────┐
                   │    qa      │ геометрия после вёрстки: ужатия, выравнивания
                   └─────┬──────┘
                         ▼
                   ┌────────────┐
                   │ evaluation │ аудит: детерминированные критерии + контраст
                   └─────┬──────┘  по рендеру
                         ▼
                   .pptx + превью + находки аудита
```

## Слои

### 1. `template_parser` — разбор шаблона
OOXML читается напрямую (python-pptx + lxml): позиции и размеры фигур, тексты и
раны с кеглями, картинки, таблицы, связи слайд→макет. Тема OOXML при этом
считается ненадёжной: ручные деки красят раны напрямую, а `theme1.xml` остаётся
офисным дефолтом, поэтому реальный стиль берётся из самих слайдов.

### 2. `design_system` — что это за шаблон
- **Кластеризация**: слайды сравниваются по мультимножествам фигур (Dice) с
  мягким штрафом по картинке рендера. Похожие слайды собираются в кластер.
- **Классификация**: LLM вызывается **один раз на кластер** (на его медоид), а не
  на каждый слайд. Рыхлые кластеры пробиваются двумя дальними членами и при
  расхождении расклеиваются. Результат кэшируется между шаблонами по отпечатку
  слайда с версией классификатора.
- **Стиль-профиль**: палитра фонов измеряется по рендерам, из неё выводится
  ротация цветов по колоде и «книжные» слайды (обложка/закрытие).
- **Стиль-карта**: один LLM-вызов на шаблон даёт словесный дизайн-бриф (тон,
  длины текстов по ролям, чего избегать). Это подсказка для генерации текста, а
  не источник жёстких ограничений.

### 3. `template_spec` — что можно заполнять
Для каждого архетипа собираются слайды-кандидаты и их ёмкость: сколько пунктов
помещается и какой длины может быть пункт (считается по метрикам шрифта и
реальной ширине слота, а не по числу символов в образце дизайнера). Здесь же
отсекаются слайды, которые заполнять нельзя: с нативной таблицей или диаграммой,
с блок-схемой, с диаграммой, собранной из фигур, — их данные принадлежат
дизайнеру, и мы не умеем их пересчитывать.

### 4. `content_parser` — план и текст
Двухфазная генерация: сначала **план колоды** (роли слайдов, темы, число
пунктов), затем **текст каждого блока** под ёмкость уже выбранного слайда.
Жёсткие ограничения (число пунктов, обязательный заголовок, максимум
разделителей, одно закрытие в конце, отсутствие переменных-заглушек в тексте)
проверяются кодом с повторным запросом, а не просьбой в промпте: модель
формулировки не соблюдает. Промпты лежат в `prompts/` отдельными файлами с
версией в имени.

### 5. `matcher` — какой слайд под какой блок
Слайд выбирается **до** генерации текста, чтобы текст писался под конкретную
ёмкость. Порядок: ёмкость → цвет из ротации шаблона → round-robin внутри семьи.
Закрытие может клонировать уже использованный слайд ради брендовой «рамки» колоды.

### 6. `generator` — вёрстка
Самый большой слой и основной носитель качества:
- текст раскладывается по **слотам** (абзацам с образцовым текстом), а не по
  первым N абзацам: ручные деки разделяют пункты пустыми спейсерами;
- кегль подбирается по реальным метрикам шрифта с учётом жирности, межстрочного
  интервала и внутренних полей бокса;
- отдельные правила для дисплейных показателей, карточных сеток, списков с
  иконками, бегущей шапки и номеров страниц;
- недостающие роли **синтезируются** на клон-канве шаблона: фон, шапка и поля
  берутся у самого шаблона, а не придумываются;
- авторские заглушки и демо-картинки снимаются: картинка в слоте заменяется
  честной рамкой «ИЗОБРАЖЕНИЕ» с описанием.

### 7. `qa` — геометрия после вёрстки
Общий проход по готовой колоде: ужатие текста под его рамку, вывод текста внутрь
слайда, обход боковых картинок, снятие ненужных мягких переносов, выравнивание
кеглей между клонами одного слайда. Этот слой работает уже после филлеров и
является последней инстанцией по кеглю.

### 8. `evaluation` — аудит
Около тридцати критериев по рубрике: геометрия (выход за край, наложения полос
текста, переполнение), типографика (мелкий кегль, разрывы слов, висячие строки),
шаблон (заглушки дизайнера, чужие данные), содержание (все ли числа слайда есть
в исходных материалах). Контраст измеряется **по рендеру**, а не по XML: схемные
цвета проходят через карту цветов мастера, и XML систематически врёт. Там, где
измерение невозможно (текст поверх картинки), аудит обязан назвать причину, а не
молчать. Подробности — в [AUDIT.md](AUDIT.md).

### 9. `rendering` и экспорт
Превью слайдов — LibreOffice headless → PDF → pdftoppm → PNG. Выход сервиса —
`.pptx` с нативными объектами: текст остаётся текстом, фигуры фигурами, слайд
никогда не выгружается единой картинкой.

## Как принимались решения

Правила вёрстки не придумывались «из общих соображений»: каждое выведено из
замера по корпусу из 13 реальных шаблонов и закреплено тестом, который падает на
коде до правила. Отменённые гипотезы сохранены вместе с причиной отката —
журнал в [improvement_runs/](improvement_runs/) (150+ итераций: что увидели на
рендере, что померили, что изменили, что откатили и почему).
